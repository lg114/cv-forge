# 重写规则（锤打成形）

## 职责 → 成果

核心转换：**动作 + 原料 → 结果 + 证据**。

- STAR（情境-任务-行动-结果）用于段落式描述；简历 bullet 用压缩变体：**做了什么（行动）→ 关键决策/难点 → 带来什么（结果）**
- 没有数字时的定性降级路径：精确数字 > 量级（"数万级用户"）> 可感知结果（"xx 流程从天级缩短到小时级"）> 删除
- 量化不只指性能数字：用户量、数据规模、团队规模、迭代次数、覆盖范围、时间节省、故障率下降都是

## 反模板化

检查重写稿：连续 bullets 若开头动词、句式结构雷同，重排。

保留用户原始语气与细节：
- 用户写得糙但有味道的表述（如"一个人扛了整个后端"）→ 精炼但保留质感，不替换成"独立负责后端全部模块的开发与维护"
- 用户的行业黑话/领域细节是真实性的来源，保留

常见中文简历雷区句式（重写时替换）：

| 雷区句式 | 问题 | 处理 |
|---|---|---|
| "负责 xx 的开发和维护" | 只有动作没有结果 | 补结果或技术决策 |
| "参与 xx 项目" | 贡献边界不清 | 写清"我"具体做了什么 |
| "精通 xx" 滥用 | 面试会被任意深挖 | 只用于真能深挖的领域；其余改为"在 xx 场景使用 xx 解决了 xx" |
| "提升了效率/性能" | 无法验证 | 指明哪个环节、从多少到多少 |

## 示例锚定

重写质量以示例为下限锚，输出方差靠它收敛。示例仅供风格锚定，具体事实永远以用户素材为准。

**例 1：职责 → 架构决策 + 结果（社招/技术岗典型）**

> Before：负责 bagger 项目的后端开发
>
> After：独立设计 (source, id) 复合主键的多 parser 架构，支撑 claude/codex 双来源 ~1.8 万条事件在单一 SQLite 中共存，新增数据源只需注册 parser 不动存储层

要点：动作（独立设计）→ 关键决策（复合主键解耦多来源）→ 可验证结果（~1.8 万事件共存 + 扩展性收益）。"负责开发"四个字里没有一个信息是筛选者能用的。

**例 2：边界模糊 → 贡献清晰 + 定性降级（无精确数字时）**

> Before：参与 RagMate 知识库项目，负责部分前后端功能
>
> After：独立完成 FastAPI 后端与前端检索界面，采用单进程部署规避多服务运维成本；基础设施（Milvus / PostgreSQL / Redis）用 Docker Compose 一键拉起

要点："参与/部分"是贡献黑洞，必须落到"我做了哪块"；没有运行数据就降级为架构决策的可感知收益（部署复杂度），不硬编数字。

## 删减与一页纸压缩

删减优先级（从前往后删）：

1. 与目标岗位无关的经历细节——压缩成一行，不是整段删
2. 重复证明同一能力的 bullets——留最强的一条
3. 教育板块非核心信息（无关课程、低于门槛的绩点）
4. 自我评价——多数是空话，能删则删；保留则每条都要有信息量
5. 项目描述中的技术背景交代——面试官懂的部分不写

压缩原则：**砍 bullet 不砍项目**（项目数量体现广度，bullet 质量体现深度）；先合并同义 bullet，再删低价值 bullet。

## 技能栏写法

技能栏回答"我能用它做什么"，不是"我碰过什么"。重写规则：

- **按能力域分组**（如 后端 / 前端 / 数据与基础设施），不按接触时间或热度罗列；单行逗号连写到十几个的，拆组或删
- **每条强项必须有项目证据**：技能栏宣称的强项，项目经历里要能找到对应 bullet；找不到的降层或删除，不留在栏里当面试靶子
- **分层动词口径统一**：精通 = 可被任意深挖（原理/源码/踩过的坑），熟悉 = 能独立完成生产任务，了解 = 用过但不主动宣称。层级拿不准时逐条问用户，不替用户拔高
- **强项带场景限定**比裸名词有信息量："Python——主力语言，Pydantic v2 / FastAPI 生产项目"优于"精通 Python"
- **定向/定制模式下技能栏排序对齐目标画像/JD** 的关键词顺序；画像/JD 没提的技术不动它原来的位置，硬塞反而暴露凑词

示例（Before → After）：

> Before：精通 Python，熟悉 Java，了解 Go；会使用 MySQL、Redis、Git、Docker
>
> After：后端：Python（主力，FastAPI / Pydantic v2 生产项目）、SQL（SQLite FTS5 全文检索调优）；基础设施：Docker Compose 多服务编排、Git

要点：分组后每条都带证据锚点；Java/Go 只有接触史、无项目证据，移出（或按用户意愿降为"了解"并接受被问的概率）。

## 公开材料（开源项目）的写入口径

用户提到开源项目时，可读取公开材料（README、代码、CI 配置）核实事实，但写入简历按以下口径：

- **结构性数字**（star 数、技术选型、架构组成等仓库事实）：经用户确认即可写
- **使用数据**（用户量、访问量等运行数据）：默认不写，除非用户明确给出认可口径
- **来自 repo/CI 但用户未亲口确认的技术细节**：写入时标注「待确认」，逐条经用户确认后转正，不默认成立
- **项目定位与成果表述**：以用户确认口径为准，公开材料只作事实核对，不作为简历内容的直接来源

## 快车道：单段改写输出格式

1. 改写后版本
2. 一句话说明改了什么、为什么
3. 若缺关键信息，提一个追问（最多一个，不升级成全卷流程）；用户明确表示"别问了，就按现有信息改"时，直接按降级路径处理并在结果中标注"信息不足，建议后续补充"
