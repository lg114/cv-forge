# 取材规则（备料）

把用户给的简历变成**可逐字引用的纯文本**，再进诊断。取材是流程的第 0 步，做不好会把后面的诊断全部带偏。

## 三条原则

1. **先取材，后诊断**：没拿到文本就不要点评。只看到文件却输出"你的简历问题在于…"，等于凭空诊断。
2. **提取物 ≠ 用户原文**：它是机器读出来的中间产物，可能乱序、可能误读。凡是可能出错的字段，按下方校验清单回读确认，宁可多问一句。
3. **本 skill 只看内容**：输入是图片或 PDF 时能看到排版问题，但那不在本 skill 范围内——最多一句话提示"排版问题建议另找排版工具"，不展开、不顺手诊断视觉。取材也不做格式还原。

## 各形态的取材路径

| 输入形态 | 首选路径 | 这条路上最容易翻的车 |
|---|---|---|
| 纯文本 / Markdown | 直接使用，保留用户原始分节与层级 | 用户常常只贴了**一段**而不是整份——先确认范围，再决定走哪条车道 |
| `.docx` | 用环境自带的文档读取能力；退路是解包后读 `word/document.xml`，去标签取文本 | **文本框与表格里的内容容易整块漏掉**——分栏模板习惯把经历塞进表格；页眉页脚里的联系方式也要单独确认 |
| `.doc`（旧二进制格式） | 通常读不了 → 请用户另存为 `.docx` / PDF，或直接粘贴 | 不要拿乱码结果硬猜内容，宁可让用户花 10 秒另存 |
| PDF | 用环境自带的 PDF 读取能力；退路是 pypdf 之类的脚本提取 | **双栏模板会让文本乱序**：板块标签与内容错位、左右栏文字互相穿插 |
| 图片 / 截图 / 扫描件 | 用环境自带的多模态读图能力直接读 | 分辨率低、手写体、艺术字会导致数字与字母误读；中文标点在识别时容易丢 |

**乱序的处理**：先按板块重组（教育 / 经历 / 项目 / 技能），再进诊断。结构无法确定时向用户确认，**不基于乱序文本下诊断结论**——那会输出一堆用户看着莫名其妙的"问题"。

**提取失败时的降级阶梯**（三级，别卡在某一级）：

1. 用环境自带的读取能力直读
2. 退路：用脚本提取（`.docx` 解包、pypdf）。**不因此给环境新增依赖；确实需要安装，先问用户**
3. 仍失败 → 请用户粘贴文本或另存为可读格式

同一阶梯适用于 JD：链接抓取失败就请用户粘贴 JD 原文，不让流程卡在链接上。

## 校验清单（提取后必做）

逐项回读下列字段并向用户确认。这些字段错了就是**实质性错误**（手机号写错会直接失联），而它们恰好是提取最易出错的地方：

- **联系方式**：手机号、邮箱、GitHub / 个人站链接
- **日期与时间线**：起止年月、工作/在校年限（错了会与第 0 步的场景判断互相矛盾）
- **数字**：团队规模、百分比、量级
- **专有名词**：公司名、学校名、项目名、技术栈名称

处理方式：把不确定的字段**列出来**问一次原文（"这边读到的是 X，对吗？"）；**不自行纠正、不按"看起来像"补全**。确认结果直接用于重写稿。

> 为什么单列一节：乱序与误读是**机器提取的特征性缺陷**，不是用户写错。把它当"待确认项"处理，而不是当"诊断发现"，否则会让人以为自己的简历错了一堆。

取材结果不单独交付，直接进诊断。确需落盘作为工作底稿时，遵守「输出规范」的落盘与隐私口径；图片 / PDF 里的证件照、身份证号、家庭住址不复述、不落盘，除非用户主动要求处理。
